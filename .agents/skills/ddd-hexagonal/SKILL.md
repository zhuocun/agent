# DDD Hexagonal Architecture

Design and assess backend systems as textbook Domain-Driven Design (DDD) with hexagonal (ports and adapters) architecture, through responsibilities, business guarantees, reachable failures, and verifiable decisions. Deliver architecture conclusions, correction options, and an acceptance procedure. When a request mixes architecture decisions with other work, such as line-by-line code review, apply this skill only to the architecture decisions. Do not turn architecture review into line-by-line code review or implement, merge, or deploy without authorization.

Apply this priority order: **effective requirements and authorization > business correctness and data protection > honest consistency and failure guarantees > evidence and operability > DDD and hexagonal fidelity, boundaries, and evolution > minimum sufficient complexity > presentation**.

## Standing Rules

These rules hold throughout the task. Each bullet carries the number of its pass clause; the rest of that clause is in its reference file (Reference Files).

- **1.1** Distinguish repository obligations from this skill's default standard and other guidance: report a fidelity deviation against its named rule with the faithful form as the recommended direction, never as an undocumented repository violation. Implementation does not lower the target, and design does not prove implementation; label changes to approved decisions as proposals. Propose justified changes to rules, documents, and guards together; never weaken correct constraints to fit code.
- **1.2** Repetition, agreement, reviewer identity, and producer self-assessment do not prove a claim.
- **1.4** Obtain scope authorization before touching protected objects; separate unrelated functional fixes.
- **1.5** Neither implementation nor review silently freezes an unresolved choice, and already authorized corrections receive no invented approval gate.
- **1.6** Registration is not approval. Local permission does not exempt a category or survive expired conditions.
- **9.3** Isolate writes, charges, notifications, deletion, and irreversible effects, or explicitly authorize and bound them; deployment permission is not destructive-test permission. Plans/estimates are not execution; respect read-only limits.

## Hold The Default Standard

Hold every backend design and review to the most faithful, textbook form of DDD and hexagonal architecture: the form that passes the strictest principal-architect review with no architectural compromise. Decide direction by this standard, principle, and best practice. Use implementation, migration, or rewrite cost only to choose among equally faithful options and to sequence and phase the work, and existing code only to sequence and phase the work; never use either to retain a weaker form or to exclude an option because the option requires rewriting. Where an effective requirement deliberately sets another form, follow it and report each difference as a deviation from this standard with its convergence direction. Never call a weaker or transitional form strict DDD or hexagonal. Express ports and other elements with whatever construct the language or runtime offers (interface, protocol, function signature, module boundary, message contract); the rules govern roles, ownership, and dependency direction, and apply equally to request-driven, event-driven, and batch backends.

Apply these fidelity rules; cite them by number in findings:

- **F1 Contexts.** Each bounded context owns its facts, rules, and glossary; the context map names actual inter-context relationships. A foreign model enters only through an anti-corruption layer or a deliberately chosen conformist or published-language relationship. Logical contexts need no separate deployable, process, or database; shared deployment does not waive their source boundaries.
- **F2 Layers and direction.** Organize four logical layers: domain, application, inbound interfaces (driving adapters), and infrastructure (driven adapters), plus a composition root that is not a business layer. The *core* is the domain and application layers; adapters and the composition root lie outside it. Domain and application remain framework-independent and depend inward on permitted domain types and core-owned ports, never outer implementations. Driving adapters access the core only through inbound ports and permitted contract types; driven adapters implement outbound ports. Only the composition root selects and binds concrete implementations across these boundaries; code may reference concrete types and collaborators within its permitted responsibility. Read and write use cases do not depend on each other, and no port depends on its implementation.
- **F3 Domain purity.** The domain layer has no framework, container, storage, transport, serialization, or ambient clock dependency. It consumes facts as values and never queries, calls out, or parses protocols.
- **F4 Aggregates.** Change aggregate state only through the root, which enforces its invariants before mutation. Reference other aggregates by identity. Prefer one aggregate per transaction; when one use case must change several atomically, redraw the boundary around the shared invariant or record a bounded exception, and add no eventual-consistency machinery without a requirement. Keep creation and reconstruction from storage as distinct entries; reconstruction restores a snapshot and is never an alternate business write. The root registers the business records and domain events required by the use case. Persist records that belong to the atomic write set with the guarded state change; apply each event's required durability and handoff contract (3.6, 6.1, 6.7), without inferring durable event storage from the existence of a domain event. Any loaded concurrency revision travels with its snapshot.
- **F5 Inbound ports.** Give each use case an explicit inbound operation with inbound-owned command or query/condition and result types. Give each use case its own port; group related use cases by letting one application service implement several ports, never by merging ports for cohesion, a shared resource, or a shared authorization boundary. Only a genuinely simple data service may share one port, and only when its written omission record names the merged use cases. Only application services (command or query handlers) implement inbound ports. Require neither one method/handler per port nor mirrored paths. Recursively inspect signatures and reachable member types: no outbound-port, adapter, handler, storage/transport, telemetry-helper, or aggregate-representation types. Permit immutable value objects that the effective baseline or recorded design allows without exposing aggregate snapshots or internal orchestration.
- **F6 Application services.** Implement inbound ports, never outbound ports. Orchestrate only the steps required by the use case: obtain facts through consumed outbound ports, obtain authorization facts and evaluate pure policies where access restrictions apply, delimit required transactions, invoke applicable domain behavior, and persist or publish only when required. Read-only and simple data use cases need no aggregate, domain service, write, or event merely to satisfy this rule. Hold no business rule, and do not wrap whole use cases in generic authorization or transaction decorators that hide required ordering.
- **F7 Outbound ports and repositories.** The core declares outbound ports in its own language only for capabilities it consumes. Assign each outbound port one owning core layer under a consistent policy per context (repositories commonly with the domain model, other capabilities with the application); the domain model never invokes them (F3). Recursively inspect signatures and reachable member types: use permitted core-owned capability and domain types, never inbound, adapter, storage, or transport types. Default to a repository as an outbound port per aggregate root, loading and saving it whole, not a table-shaped or generic data-access facade. If a stated guarantee requires distinct loading and write scopes (for example, a write capability that must be unusable outside its transaction, or a consistent load whose read set exceeds one aggregate), allow separate load and transaction-scoped write capabilities; obtain the latter only within its issuing transaction, and prevent escape or reuse afterward. Keep required business records atomic with the guarded state change (F4, 6.1-6.4). Query use cases obtain facts only through read capabilities that return immutable projections or snapshots owned by the core; they never load an aggregate through its repository or any write-side capability, even without saving. Adapter-only technical collaboration gets no core port and is wired at assembly. A standard-library source of ambient runtime values, such as a clock, needs no core-owned port; the composition root creates and injects it, and the domain receives only its values (F3).
- **F8 Adapters.** Driving adapters (request handlers, remote-call endpoints, message consumers, schedulers, command lines) limit dependencies on the core to inbound ports and permitted contract types, never concrete application services, outbound ports, or domain internals; they do not call driven adapters. They may use their own transport libraries and helpers to translate protocols and extract trusted identity. When implementing core contracts, infrastructure implements only outbound ports, never inbound use cases or domain judgment; all outbound-port implementations belong there. Storage and remote representations stay inside driven adapters. Adapter-local helpers need no port.
- **F9 Composition root.** Keep it apart from business layers. Construct and inject dependencies explicitly, select a unique implementation for each required port binding and profile, preserve required instance identity and lifetime when several ports share one service, and fail explicitly on a missing required implementation. The core performs no service location or implicit discovery.
- **F10 Interfaces and patterns.** Inbound and outbound ports may have one implementation because they are boundaries. Every other single-implementation interface, factory, strategy, builder, or pure forwarding wrapper needs a present structural reason.
- **F11 Physical organization.** Modules, packages, namespaces, or directories make contexts and layers visible, so the tree communicates the architecture and guards can target it; empty layers, mirrored inbound/outbound trees, and one directory per class are not required. Correct code in a misleading structure is a fidelity finding.
- **F12 Enforcement.** Require executable architecture guards for affected stable source-level boundaries claimed by F1-F3, F5, and F7-F9 where the stack supports them; otherwise record an equivalent check with procedure, inspected scope, evidence, result, and limits. Use meaningful violating and legal samples (9.2). Judge modeling and necessity by review; prove business invariants, transaction lifetimes, and runtime guarantees through appropriate semantic tests. State each proof's limits; static guards prove neither runtime isolation nor business correctness, and design-only checks remain planned until executed.

Fidelity does not mean more structure. Every element answers a present invariant, boundary, use case, consumer, or reachable failure; hypothetical future flexibility is not necessity, and ongoing structure without a present need is a defect whatever it cost to build. Add dedicated read models, event sourcing, sagas, separate stores, messaging infrastructure, or extra layers only for a present requirement. Rigor is never overdesign: do not remove real validation, failure classification, concurrency guards, readable names, or effective negative tests merely to reduce code. Any context or component may omit a tactical element (an aggregate with its repository, an entity, a domain event, or a domain service) that no present invariant, lifecycle, consumer, or boundary requires, for example a genuinely simple data service or a technical pipeline whose rules are parsing, routing, transformation, and delivery rather than business invariants. Omitting aggregates requires a written omission record naming each omitted element, showing why no invariant or boundary requires it, and stating a reconsideration trigger; elements added only on need (domain events, domain services, anti-corruption layers) need no record when that need is absent. Subdomain type alone neither requires nor waives an element; invariants decide (F4). Assess actual invariants and model needs; competing writers or a foreign dependency alone do not require aggregates, domain events, or domain services. Omission never relaxes inward dependencies, domain purity, adapter/port role separation, authorization, failure guarantees, or verification.

## Select The Review Depth

Run the basic path: establish mandate and impact closure, challenge mechanism necessity, inspect affected responsibilities/contracts against the default standard, and report evidence and limits. Classify as **Basic** when tracing excludes changed guarantees and reachable specialist risks; **Focused** when a specific risk is reachable; **Consequential** when reachable failure threatens material data loss, unauthorized effects, or required cross-boundary, availability, or recovery guarantees. Simple localized work without those risks uses only the basic path; size alone does not establish safety. Basic narrows scope and reporting, not the fidelity bar.

Deepen only affected paths, including proposed design paths. Record triggers and selected clauses; reuse valid evidence for unchanged guarantees. Infrastructure elsewhere does not trigger a system-wide audit. Mark exclusions `Not applicable: <reason>` with tracing grounds and missing proof `Unknown`. Create no mechanism merely because a pass names it.

- **Structure and fidelity:** created, changed, or drifted contexts, aggregates, ports, adapters, dependencies, physical organization, or composition trigger Passes 2.4-2.5 and 3 with the matching fidelity rules, and 9.2 for their guards.
- **Data and state:** changed fact meanings, representations, lifecycle entries, or durable writes trigger relevant Passes 4-6; apply time and numeric checks only where correctness depends on those values.
- **Concurrency and integration:** shared mutable state, competing invariant updates, cross-process calls, required propagation, or message consumption trigger matching concurrency, delivery, deadline, overload, and resource checks.
- **Operations and protection:** affected resource use/retention, access restrictions, sensitive flows, promised deletion, caches, dangerous operations, or availability/recovery assumptions trigger matching checks in Passes 5 and 7.
- **Evolution and proof:** affected published contracts, durable formats, support windows, mixed versions, or configuration transitions trigger Pass 8 and compatibility evidence; architecture guards trigger 9.2 and high-consequence guarantees trigger 9.5.

## Deliverable

Use applicable slots in order; combine headings when useful. For Basic work, retain concise scope/baseline and obligation/evidence rows, the decision or findings, and evidence/status. Keep the review arrangement (2) in every report. Omit candidate records/dispositions (3-4) when no candidates exist, owner-choice rows in (5) when no unresolved owner choices exist, correction/release planning (6) when neither is proposed, compatibility matrices (7) when tracing excludes affected supported boundaries, and measurements within (8) if no relevant change or claim exists. For Basic work, one grounded scope statement may explain all omitted slots; otherwise give each omitted slot one sentence `Not applicable: <reason>`. Missing required work is pending, not inapplicable.

Focused reports include triggered proofs; Consequential reports expose decision-driving scenarios, failure evidence, and residual risks separately. Explicit effective reporting obligations override shortcuts. Accept a decision or review report separately from correction or release acceptance. Keep only actually required adjudication, independent-review, or execution gates pending; do not invent gates.

## Reference Files

The passes and Deliverable slots are in four reference files, which keep their clause numbers. Also read the file that holds any clause a rule cites by number.

- `references/design-and-structure.md` (standard vocabulary, Passes 1-3, 9.1-9.2): at the start of every task, because 1.1-1.6 serve the basic path's mandate and impact closure and the basic path's necessity challenge is 2.2; and when **Structure and fidelity** applies or **Evolution and proof** triggers 9.2. Read it in full before applying any of its clauses, and again after a context compaction.
- `references/state-and-concurrency.md` (Passes 4-6): when **Data and state** or **Concurrency and integration** applies, or **Operations and protection** triggers a Pass 5 check. Read it in full before applying any of its clauses, and again after a context compaction.
- `references/operations-and-evolution.md` (Passes 7-8): when **Concurrency and integration** triggers a deadline, overload, or resource check, **Operations and protection** triggers a Pass 7 check, or **Evolution and proof** triggers Pass 8. Read it in full before applying any of its clauses, and again after a context compaction.
- `references/reporting-and-proof.md` (Deliverable slots 1-8, 9.3-9.5, worked omission records): before writing any report, running or claiming any validation, writing reusable instructions, or writing an omission record, and when **Evolution and proof** triggers compatibility evidence or 9.5. Read it in full before applying any of its clauses, and again after a context compaction.
